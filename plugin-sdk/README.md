# ShipFlow Plugin SDK

Extend ShipFlow with custom risk calculators, report generators, and integration providers.

> **How plugins actually run**: ShipFlow plugins are ordinary Spring beans **compiled into the
> backend build** — there is no dynamic runtime JAR loading (no `plugins/` directory that gets
> scanned, no classloader magic). Writing a plugin means: generate a project from the archetype
> below, implement one of the three SPI interfaces, then add your plugin project as a Maven
> dependency of the ShipFlow `backend` module and rebuild/restart. This is a deliberate scope
> decision — dynamic loading of arbitrary third-party JARs is an arbitrary-code-execution /
> sandboxing risk that's out of scope for now. See "Deployment" below for the exact steps.

## Module layout

This directory contains three real, independently-buildable Maven projects (see the root
`pom.xml` aggregator, which builds `shipflow-plugin-api` and `backend` together):

| Module | What it is |
|--------|------------|
| `shipflow-plugin-api/` | The distributable jar (`com.github.farzadsedaghatbin.shipflow:shipflow-plugin-api`) containing the 3 SPI interfaces. Plugin projects depend on this with `<scope>provided</scope>`. The ShipFlow `backend` module depends on the exact same artifact — the interfaces live in one place, not two copies that can drift. |
| `shipflow-plugin-archetype/` | A Maven archetype (`mvn archetype:generate`, see Quick start) that scaffolds a new plugin project pre-wired with the `shipflow-plugin-api` dependency and one sample class. |
| `sample-plugin/` | A hand-written, fully worked example plugin project (not generated by the archetype) — useful as a second reference alongside the archetype output. |

## Quick start

Generate a skeleton plugin project with the Maven archetype:

```bash
# 1. Build & install the two SDK modules this archetype depends on (one-time, or after an SDK update)
cd plugin-sdk/shipflow-plugin-api && mvn install && cd -
cd plugin-sdk/shipflow-plugin-archetype && mvn install && cd -

# 2. Generate your plugin project from the archetype
mvn archetype:generate \
  -DarchetypeGroupId=com.github.farzadsedaghatbin.shipflow \
  -DarchetypeArtifactId=shipflow-plugin-archetype \
  -DarchetypeVersion=1.0.0 \
  -DgroupId=com.example \
  -DartifactId=my-shipflow-plugin \
  -Dversion=1.0.0-SNAPSHOT \
  -DinteractiveMode=false
```

This generates `my-shipflow-plugin/` with a `pom.xml` already depending on `shipflow-plugin-api`
and a sample `RiskCalculatorPlugin` implementation under `src/main/java/com/example/`.

## Available SPI interfaces

| Interface | Package | Purpose |
|-----------|---------|---------|
| `RiskCalculatorPlugin` | `com.github.farzadsedaghatbin.shipflow.plugin` | Augment AI risk scoring for pitches |
| `ReportGeneratorPlugin` | `com.github.farzadsedaghatbin.shipflow.plugin` | Generate downloadable reports (PDF, CSV, XLSX) |
| `IntegrationProviderPlugin` | `com.github.farzadsedaghatbin.shipflow.plugin` | Send/receive data from external services |

## Minimum `pom.xml`

```xml
<dependency>
  <groupId>com.github.farzadsedaghatbin.shipflow</groupId>
  <artifactId>shipflow-plugin-api</artifactId>
  <version>1.0.0</version>
  <scope>provided</scope>
</dependency>
```

`shipflow-plugin-api` is versioned independently of the ShipFlow application/milestone version
(it's an SPI contract, not the app itself) — check `plugin-sdk/shipflow-plugin-api/pom.xml` for
the current version before depending on it.

## Example: custom risk calculator

```java
import com.github.farzadsedaghatbin.shipflow.plugin.RiskCalculatorPlugin;
import org.springframework.stereotype.Component;
import java.util.Map;

@Component
public class MyRiskCalculator implements RiskCalculatorPlugin {

    @Override
    public String getPluginId() { return "my-risk-calculator"; }

    @Override
    public String getDisplayName() { return "My Custom Risk Calculator"; }

    @Override
    public Double calculateRisk(Map<String, Object> context) {
        // context keys: pitchId, pitchTitle, appetiteDays, cycleId,
        //               taskCount, completedTaskCount, daysRemaining
        Integer daysRemaining = (Integer) context.get("daysRemaining");
        Integer taskCount     = (Integer) context.get("taskCount");
        Integer completed     = (Integer) context.get("completedTaskCount");
        if (taskCount == null || taskCount == 0) return null;
        double progress = completed.doubleValue() / taskCount;
        // Return null to abstain; return [0.0, 1.0] to vote
        return daysRemaining != null && daysRemaining < 7 && progress < 0.5 ? 0.9 : 0.2;
    }
}
```

## Deployment

There is no dynamic loading — a plugin becomes part of the compiled ShipFlow backend:

1. Build your plugin project's jar (`mvn install`, or `mvn package` + install it into a shared
   Maven repository your ShipFlow build can reach).
2. Add it as a regular dependency of `backend/pom.xml`:
   ```xml
   <dependency>
     <groupId>com.example</groupId>
     <artifactId>my-shipflow-plugin</artifactId>
     <version>1.0.0-SNAPSHOT</version>
   </dependency>
   ```
3. Rebuild and restart the ShipFlow backend. On startup, `PluginAutoConfiguration`'s
   `CommandLineRunner` discovers every Spring bean on the classpath implementing
   `RiskCalculatorPlugin`, `ReportGeneratorPlugin`, or `IntegrationProviderPlugin` and registers
   it with `PluginRegistry` — this part is genuinely automatic; you don't write any registration
   code beyond `@Component` on your class.

Once registered, enable/disable individual plugins at **runtime** from
**Organization Settings → Plugins** without restarting the application again — only adding a
*new* plugin (or removing one) requires a rebuild + restart; toggling an already-registered
plugin on/off does not.

## Admin API

```
GET  /api/v1/admin/plugins                       — list all registered plugins
PATCH /api/v1/admin/plugins/{pluginId}/enabled   — toggle enabled state
```

Both endpoints require the `ADMIN` role.
