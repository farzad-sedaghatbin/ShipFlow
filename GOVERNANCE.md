# Governance

## Project Status

ShipFlow is actively maintained by a **sole maintainer** ([@farzad-sedaghatbin](https://github.com/farzad-sedaghatbin)).

The project is open source under the [MIT License](LICENSE). Contributions are welcome and encouraged.

## Decision Making

### For small changes (bug fixes, docs, dependency updates)

Open a PR. If CI passes and the change looks correct, it will be merged — typically within a few days.

### For significant changes (new features, API changes, architecture decisions)

1. Open a **GitHub Discussion** in the [Ideas](https://github.com/farzad-sedaghatbin/ShipFlow/discussions/categories/ideas) category first.
2. Describe the problem you are solving and your proposed approach.
3. Allow time for community feedback (at least a few days for non-urgent changes).
4. Once there is rough consensus, open a PR referencing the discussion.

### For breaking changes

Breaking changes to the public API or data model require a discussion thread and will be noted in the CHANGELOG with a migration guide.

## How to Become a Contributor

1. Read [CONTRIBUTING.md](CONTRIBUTING.md) for the technical contribution guide.
2. Look for issues labelled [`good first issue`](https://github.com/farzad-sedaghatbin/ShipFlow/labels/good%20first%20issue) or [`help wanted`](https://github.com/farzad-sedaghatbin/ShipFlow/labels/help%20wanted).
3. Comment on the issue to let others know you are working on it.
4. Open a PR targeting `main`.

Consistent, high-quality contributors may be invited as maintainers over time.

## Response Time Expectations

This is a best-effort open-source project maintained in personal time. There are **no SLA commitments**.

| Activity | Typical response |
|----------|-----------------|
| Bug reports | A few days to a week |
| Feature requests | Reviewed when planning next milestone |
| PRs (small) | A few days |
| PRs (large) | 1–2 weeks |
| Security issues | See [SECURITY.md](SECURITY.md) — prioritized |

If you need a faster response for a critical bug, comment on the issue to draw attention.

## Security Vulnerabilities

**Do not open a public GitHub issue for security vulnerabilities.**

Follow the process in [SECURITY.md](SECURITY.md):
- Email the maintainer directly with details of the vulnerability.
- Allow reasonable time for a fix before any public disclosure.
- Credit will be given in the release notes.

## Roadmap

The product roadmap is tracked in [ROADMAP.md](ROADMAP.md) and in the [public roadmap page](https://shipflow.dev/public-roadmap) of the live demo.

Milestone planning happens before each release cycle. Community input via GitHub Discussions influences priorities.
